## 2. 架构图

```
createWebSocket()                      ← 唯一公开构造入口
  └─ PageWebSocketClient               ← EventTarget、onMessage 注册表、freeze/replay 缓冲
       └─ ClientTransport (接口)
            ├─ SharedWorkerTransport   ← hello/welcome/attach + lease + 请求关联
            │    ╎ MessagePort
            │    └─[SharedWorker]─ createSharedWebSocketRuntime
            │         └─ connections: Map<id, ConnectionEntry>
            │              └─ ConnectionController  ← 状态机/重连/心跳/队列/背压/revision
            │                   └─ 1 个物理 WebSocket
            └─ DirectTransport         ← 同一个 ConnectionController，走模块全局 directPool
                 └─ 1 个物理 WebSocket（仅本页 realm）
```

关键设计优点：`ConnectionController` 是 shared-worker 与 direct 的**同一份**实现，契约一致性由构造保证而非靠测试对齐（规格 §3.2）。心跳、队列、重连状态都挂在 controller 上，即每物理连接一套，符合 §15「每个物理连接只能有一套 heartbeat timer」。

## 3. P1 — 建议发布前修复

### [P1] 控制信封字节计算不递归：合法二进制发送杀掉共享 port，超大 buffer 完全绕过限制

- **File**：`packages/core/src/worker-runtime.ts:68-83`（`estimateBytes`），在 `:379-387` 执行
- **证据与触发条件**：`estimateBytes` 对**信封对象**做类型判断，而信封永远不是 string/Blob/ArrayBuffer/view，因此总是落到 `JSON.stringify` 分支。实测（直接复制源码函数运行）：

  ```
  send + Uint8Array(256KiB)   estimate=3,296,802  → 超 2MiB 上限 → port 被 detach
  send + ArrayBuffer(8MiB)    estimate=41         → 放行
  send + Blob(8MiB)           estimate=41         → 放行
  cyclic envelope             estimate=0          → 放行（catch→0）
  ```

  typed array 被序列化成 `{"0":12,"1":200,…}`，膨胀约 10.5 倍。
- **影响**：两个方向同时错。正常的 256KiB 二进制业务消息会导致**该 tab 的 MessagePort 被直接关闭**（而非返回 `MESSAGE_TOO_LARGE`），该 tab 静默失去共享连接；同时 8MiB payload 畅通无阻，§21.1 的 `maxControlEnvelopeBytes` 上限形同虚设。
- **规格关系**：违反 §21.1 资源上限；违反 §13.4（string/Blob/ArrayBuffer/view 必须全部支持）
- **修复方向**：递归累加 `data` 字段的真实字节数，复用 `bytes.ts:socketDataByteLength`
- **建议测试**：unit —— 断言 256KiB typed array 不触发 detach，8MiB ArrayBuffer 被正确拒绝

### [P1] 未 attach 的 port 永不回收，256 port 预算被永久占用

- **File**：`packages/core/src/worker-runtime.ts:162-166`（`detach`），回收路径 `:369-377`（`connect`）
- **证据与触发条件**：`detach()` 开头 `clients.get(port)` 对未完成 hello 的 port 返回 `undefined`，函数**提前 return**，因此永远走不到 `connectedPorts.delete(port)` 与 `port.close?.()`。实测：

  ```
  3 个 port 只 connect 不发 hello → 回收 timer 注册 3 个（正常）
  触发全部回收 timer → ports closed: false,false,false   （期望 true,true,true）

  256 个未完成 hello 的 port + 全部回收 timer 触发后：
  第 257 个健康 tab connect → port 立即被关闭
  ```
- **影响**：脚本慢、页面在握手中被关闭，或被上一条 bug 打死的 port，都会永久占用配额。累计 256 次后，**该 origin 下所有新 tab 都无法接入共享连接**，且无任何诊断信号。SharedWorker 在所有页面关闭前不会重启，故该状态不可自愈。
- **规格关系**：违反 §21.1「un-attached port 必须在超时后回收」
- **修复方向**：把 `connectedPorts.delete` / `port.close()` / 清 timer 移到 `client === undefined` 的提前 return 之前
- **建议测试**：unit —— 未 hello 的 port 在 `unattachedPortTimeoutMs` 后被关闭且配额被释放

### [P1] `fallback: 'error'` 泄漏 DirectTransport，污染模块全局 directPool

- **File**：`packages/wws/src/index.ts:87`（无条件构造）、`:102-108`（仅 `fallback==='direct'` 时接线）、`packages/core/src/direct-transport.ts:47,60-79`
- **证据与触发条件**：`createDirectFallback()` 在 `:87` **无条件**执行，其构造函数立即在模块全局 `directPool` 注册条目；但 `:105` 只在 `fallback === 'direct'` 时把它交给 transport。`fallback: 'error'` 时该对象成为孤儿，永远收不到 `dispose()`，refcount 永不归零。实测：

  ```
  CASE A（fallback:'error'，3 次 create + dispose）
    再用同 id 不同 config → CONNECTION_CONFIG_CONFLICT   ← 条目从未释放
  CASE B（默认 fallback:'direct'，3 次 create + dispose）
    再用同 id 不同 config → OK                            ← 正确释放
  ```
- **影响**：选择 `fallback: 'error'`（即「第二条物理连接不可接受」的严格用户）的应用，即使正确调用 `dispose()`，之后用同一 id + 新配置重建连接会被伪造的 `CONNECTION_CONFIG_CONFLICT` 拒绝。SPA 内换 endpoint/binaryType 的重连场景必现。
- **规格关系**：违反 §7 `dispose()` 终态语义；伪造 §6.2 的冲突判定
- **修复方向**：改为惰性构造 —— 仅当 `fallback === 'direct'` 时才 `new DirectTransport`
- **建议测试**：integration —— `fallback:'error'` 下 create/dispose 后，同 id 新配置可正常建立

## 4. P2 — 建议修复

### [P2] `overflow` / `INBOUND_OVERFLOW` 永远到不了页面

- **File**：`packages/core/src/worker-runtime.ts:317` 发出，`packages/core/src/shared-worker-transport.ts:331-358` 从不处理
- **证据**：worker 正确 post `{type:'overflow',direction:'replay',droppedMessages,droppedBytes}`，`control.ts:83` 的 `isWorkerControlMessage` 也接受该类型，但 `handleMessage` 只分支 response/state/open/message/close/error；`ConnectionSink`（`connection-controller.ts:30-37`）根本没有 `onOverflow` 成员，消息被静默丢弃。`INBOUND_OVERFLOW` 仅存在于 `errors.ts:34` 的码表中，全仓无一处构造。
- **影响**：默认 transport 下，应用无法感知 worker 在 suspend 期间丢弃了入站消息 —— 而这正是 restore-replay 丢数据的唯一信号。
- **规格关系**：违反 §14（credit 耗尽须发 `INBOUND_OVERFLOW`/overflow）、§10.4（回放溢出须通过 overflow/diagnostic 暴露）
- **修复方向**：`ConnectionSink` 增加 `onOverflow`，transport 加 `overflow` 分支，页面侧派发已定义好的 `WwsOverflowEvent`
- **建议测试**：integration —— suspend 期间灌满回放缓冲，restore 后断言页面收到 `overflow` 事件

### [P2] `limits.maxPortsPerWorker` 与 `unattachedPortTimeoutMs` 配置被忽略

- **File**：`packages/core/src/worker-runtime.ts:374`（用 `DEFAULT_RESOURCE_LIMITS.maxPortsPerWorker`）
- **证据**：`config.ts:206-216` 正确归一化并把 `limits` 纳入 fingerprint，`connection-controller.ts:218` 也正确读取 `config.shared.limits.maxClientsPerConnection`；但 worker 的 port 层硬用 `DEFAULT_` 常量。
- **影响**：调用方收紧或放宽 port 上限、调整回收超时均无效果，且失败方式是静默的（配置进了 fingerprint，行为却不变）。
- **规格关系**：违反 §21.1「默认资源上限必须可通过静态共享配置收紧/放宽」
- **修复方向**：port 层改读连接的 `shared.limits`；pre-hello 阶段无连接归属，可保留 DEFAULT 作为兜底并在文档中说明
- **建议测试**：unit —— 自定义 `maxPortsPerWorker: 2` 时第 3 个 port 被拒

### [P2] 文档与实现矛盾：raw 协议的 activity 模式心跳不存在

- **File**：`packages/docs/guide/reliability.md:35`，实现见 `packages/core/src/config.ts`、`protocol.ts:20`
- **证据**：文档称 "The raw protocol can use activity mode"。但 `rawProtocol` 的 capabilities 是 `{auth:false, binary:true, heartbeat:false}`，而 config 归一化要求 adapter 声明 heartbeat 能力。实测：

  ```
  heartbeat: true                → THROWS INVALID_OPTIONS
  heartbeat: {mode:'activity'}   → THROWS INVALID_OPTIONS
  heartbeat: {mode:'pong'}       → THROWS INVALID_OPTIONS
  json protocol + heartbeat      → ACCEPTED
  ```
- **影响**：照文档写 raw + heartbeat 的用户会在创建时同步抛错。规格 §15 说的是「raw 协议默认不启用心跳」，实现选择了更严格的「不允许」，文档描述的是第三种不存在的行为。
- **规格关系**：文档不符 §15；实现本身可辩护（更严格），需要文档与规格对齐
- **修复方向**：三者取其一并统一 —— 建议改文档，说明心跳需要声明 heartbeat 能力的协议（JSON 或自定义 adapter）
- **建议测试**：unit —— 断言 `rawProtocol` + `heartbeat` 抛 `INVALID_OPTIONS`（把当前行为钉死）

## 5. 已驳回的结论

以下是 sub-agent 提出但经我回源码裁决后**驳回**的结论，记录以免后续误修：

**驳回：`close()` 的 `queue.clear()` 会清掉其他 tab 的待发消息（原报 P1）**
提出该结论的报告在自己的证据行里就出现了自我更正。核对 `connection-controller.ts:262-278` 的全部调用方后确认：`detach(clientId)` 走的是 owner 范围的 `queue.removeOwner()`；idle 路径 `:634-638` 有 `sinks.size === 0` 守卫；`DirectTransport.close()`（`direct-transport.ts:90-92`）只调 `detach`，不调 `close`；`dispose()`（`:122-134`）有 refcount 守卫，只在最后一个引用时才 dispose controller；worker 侧 `case 'close'`（`worker-runtime.ts:335-337`）同样只调 `detach`。**不存在可达路径**会在其他 client 仍持有队列项时清空队列。行为符合 §13.3。

**驳回：`CONNECTION_CONFIG_CONFLICT` 可能触发 direct 降级**
`shared-worker-transport.ts:42-51` 的 allowlist 不含该码，`activateFallback`（`:379-391`）对不在表内的错误直接 rethrow。行为正确，符合 §18.2 禁止列表。

## 7. 结论与建议

代码质量整体扎实：状态机、revision 寄存器、fingerprint 归一化、错误码表、脱敏、依赖治理与打包边界都严格贴合规格，`ConnectionController` 复用带来的双 transport 契约一致性是很好的架构决策。

发布前建议按此顺序处理：

1. 修 3 条 P1（信封字节计算、port 回收、directPool 泄漏）—— 前两条都会造成 tab 静默失去共享连接，是本次最实际的生产风险。
2. 补 E2E 缺口，优先「普通 socket 故障不触发 direct」与 bfcache 恢复 —— 现有 3 例 E2E 无法拦住上述任何一条 P1，这是流水线全绿却仍有 P1 的根因。
3. 打通 overflow 事件链路，否则 replay 丢数据对应用不可见。
4. 修 `verify-release.mjs` 的 `.map` 过滤缺口；对 sourcemap 是否内联私有源码作出显式决策。
5. 统一 raw 心跳的文档/规格/实现三方描述。

`limits` 部分生效（P2）与 sourcemap（P2）不阻塞发布，但建议在 v1 冻结公开语义前一并处理，因为 `limits` 已进入共享配置 fingerprint，后续改变生效范围会影响冲突判定。
