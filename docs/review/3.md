## P1：优先修复

### F01：lease 转移后，旧页面仍能启动 keyed handler

位置：`packages/core/src/worker/runtime.ts:473`、`:733`；`packages/core/src/page/client.ts:605`。契约：`packages/core/src/shared/types.ts:121`。

A、B 注册同一个 key，A 持有；A 保持 visible，但长任务阻塞主线程，暂停处理端口消息与发送 lease。Worker 已向 A 排队业务消息，随后回收其 lease 并把 key 授予 B。A 恢复处理旧消息时，页面只检查缓存的 held set 和 freeze barrier，仍会新启动 keyed handler。Worker detach 先删除 `clientsById` 再撤销 key，撤销回调也无法向 A 发送 revoke。

主审以真实 runtime、transport、page 源码配合可暂停投递的端口与注入时钟复现：B 在授权转移后处理 `after-expiry`，随后 A 处理 `queued-before-expiry`，两页 `holdsKey()` 同时为 true。这不是已启动 Promise 的副作用继续运行，而是旧页面在失去授权后新启动 handler。Node 原生 MessageChannel 另确认：发送端 close 不会撤回此前已 post 的消息。此竞态未在真实浏览器长任务场景下单独执行。

修复方向：在页面启动 keyed handler 前校验保守的授权有效期限，过期时建立验证屏障并向 Worker 确认权威。仅补发 revoke 不能覆盖排在 revoke 前面的旧业务消息。新增回归应覆盖 visible 页面停顿，而不只覆盖显式 freeze/BFCache。

### F02：关闭后等待端口回收，再次 open 会从 shared 转为 direct

位置：`packages/core/src/transport/shared-worker.ts:257`、`:514`、`:638`；`packages/core/src/worker/runtime.ts:524`。

shared client 成功 open，随后 close；等待超过 lease timeout 和 sweep 间隔，再对同一未 dispose client 调用 open。Worker 已关闭旧 port，页面却继续使用它。close 的 `resetHello()` 把 `workerInstanceId` 清成 null，下一次 hello 超时又被当作首次初始化失败，允许启用 direct fallback。

主审复现结果为 `before: shared-worker`、`after: direct`，旧 Worker port 已关闭。配置 `fallback: error` 时，同一路径会拒绝 reopen。它同时影响公开的 close 后可再次 open 契约，以及选定 shared 后恢复失败不得静默切换的边界。

修复方向：独立保存是否已经选定 shared；晚 reopen 重建 SharedWorker port 并完成权威同步。普通 open 与生命周期恢复应遵循相同的降级限制。

### F03：运行中背压入队没有冲刷触发点，后续发送越过旧消息

位置：`packages/core/src/connection/controller.ts:432`、`:507`、`:740`。契约：`packages/docs/site/guide/reliability.md:40`。

socket 已打开且初次 flush 已结束，将 bufferedAmount 提升到高水位，发送 first 并允许入队；随后缓冲下降到低水位。`enqueue()` 只增加队列，`flushQueue()` 只从 `becomeOpen()` 调用，没有后续 drain 或轮询任务。再发送 second 时直接写 socket。

主审复现：first 返回 queued；缓冲排空并推进时钟后，发送列表仍为空；second 返回 accepted，发送列表为 `[second]`，queueMessages 仍为 1，冲刷 timer 为零。已接纳消息会一直留到重连或清理，破坏 FIFO。

修复方向：open 状态背压入队时启动唯一冲刷任务；队列非空时新发送保持 FIFO；冲刷过程中每次发送后重新检查水位，不能仅在整个 drain 开始前检查。

### F04：小视图的完整 backing buffer 未计入克隆额度

位置：`packages/core/src/shared/structured.ts:226`。

`new Uint8Array(new ArrayBuffer(8 * 1024 * 1024), 0, 1)` 的有效视图只有 1 字节，估算返回 25 字节；`structuredClone(view).buffer.byteLength` 却为 8388608。类型化数组结构化克隆保留完整 backing buffer，估算只使用 `current.byteLength`。DataView 有相同问题。

主审独立复现上述数值。这使控制 envelope、delivery credit 与 replay 的内存预算严重低估。Worker 在收到控制消息前浏览器就已经完成克隆，因此接收端限制也不能被描述为浏览器分配内存前的硬限制。

修复方向：克隆/保留内存按 backing buffer 计费并对共享 buffer 去重，或在传输和存储边界复制有效视图。原生 socket 的 wire 字节数与结构化克隆的内存口径需要分别明确。

### F05：direct adapter 异常中的任意字符串 details 进入 logger

位置：`packages/core/src/shared/errors.ts:172`；`packages/core/src/page/client.ts:64`、`:650`。

合法 custom adapter 的 decode 抛出 `SocketFuseError('DECODE_FAILED', ..., { details: { token: 'credential-example', payload: 'business-example' } })`。在 direct 路径，已有 DECODE_FAILED 被保留；两次所谓脱敏都只过滤值的类型，字符串字段最终进入 onError 与 logger。

主审用真实 Page + Direct + adapter 源码复现，logger 收到完整的上述 token 和 payload 示例值。普通 Error 的 message/cause 会被移除；shared 的最终控制错误只传 code/fatal/retryable，所以不能把此问题扩大为所有 Worker 错误都泄漏。

修复方向：对不受信的 adapter 错误删除 details，或只保留由库生成且按错误码明确列出的安全字段。primitive 类型检查不构成脱敏。

### F06：旧连接的异步完成分支可污染新连接

位置：`packages/core/src/connection/controller.ts:579`、`:618`。

主审独立复现了两条路径：

1. 旧 socket 的异步 decode 未完成，新 socket 已 open；旧 decode reject 后，catch 调用 `handleError()` 没有携带 socket/attempt。新连接的 lastErrorCode 被写为 DECODE_FAILED，页面收到旧错误。
2. raw heartbeat 正在异步读取旧 Blob 并比较 pong；期间重连且新 socket 已 open。比较结束后没有再次检查代际，旧业务帧直接 fan-out。复现中 socketCount 为 2，当前状态 open，但旧 Blob 被派发。

已有 handleFrame 入口检查无法保护后续 await。修复需要在所有异步成功和失败出口重新验证 socket/attempt，并在过期分支停止派发、状态更新及错误广播。

### F07：Version Packages PR 的干净 CI 缺少 publint 前的构建

位置：`.github/workflows/ci.yml:46`；根 `package.json:29`。

Version PR 的 CI 只执行 install、check:static、release:verify，跳过包含 build 的 check:runtime。release:verify 第一项是 `publint --strict`，此时 Git 未跟踪的 dist 不存在。安装只运行根 prepare，typecheck 使用 noEmit；publint 0.3.24 的 pack 明确使用 `ignoreScripts: true`，不会执行包的 prepack 补建 dist。

主审在临时干净包目录复制当前 package.json/README/LICENSE，用同一 publint 的文件检查复现 9 个 FILE_DOES_NOT_EXIST，覆盖三个入口的 types/import 以及 main/module/types。此夹具使用 `pack: false` 隔离缺少 dist 的条件；CI 命令顺序与忽略 lifecycle scripts 的结论来自源码核验。没有实际创建远程 Version PR。

本地按 build → release:verify 顺序成功，不反驳干净 CI 的失败。应在 publint 之前显式构建，或让 release:verify 自身提供完整的构建前置条件。

## P2：运行语义与公开契约

### F08：shared open 忽略调用之后发生的 abort

位置：`packages/core/src/transport/shared-worker.ts:201`、`:223`。

入口只检查一次 `signal.aborted`，等待 hello、注册同步和 socket open 期间没有 abort listener。主审执行 open → abort → socket open，Promise 仍 resolve 为 open；direct 会拒绝对应 waiter。公开类型承诺 signal 仅取消当前等待者。应为 shared 页面本地等待者加入取消和监听清理，不关闭物理连接或影响其他 waiter。

### F09：固定 10 秒控制请求期限覆盖连接等待期限

位置：`packages/core/src/transport/shared-worker.ts:223`、`:533`。

配置合法的 `connectionTimeout: 30000`，shared open 请求仍在 10000 毫秒被拒绝为 WORKER_DISCONNECTED。主审注入请求时钟复现该拒绝，随后打开 socket，页面又转为 OPEN。direct 等待由连接状态机控制。慢异步 send 也可能先请求超时、后实际发送，令调用方难以解释结果。

应区分控制通道探活与 open/send 操作等待。open 的完成、失败与取消须由其公开契约及连接状态机共同决定，不能统一套固定 10 秒请求 timer。

### F10：logger 抛错会打断 handler 和状态机隔离

位置：`packages/core/src/page/client.ts:620`、`:653`。

handleError 在 try 外调用 logger。第一条 message handler 抛错时，如果 logger 再抛错，dispatchMessage 会在第二条 handler 与 EventTarget message 前退出。主审直接调用真实页面派发路径复现，调用记录只有 first，异常为 logger failed。direct 的 controller error sink 同样调用此路径，可能打断后续状态推进；异步 handler reject 分支还可能产生新的未处理 rejection。

应单独 try/catch 隔离 logger，且不向同一个 logger 递归报告其自身异常。

### F11：扩展准备计划取消和 runtime dispose 不终止 signal/timer

位置：`packages/core/src/worker/runtime.ts:335`、`:364`、`:714`。契约：同文件 `AttemptPreparationContext.signal`。

扩展 abort controller 和 deadline timer 只存在于 `startExtensionPreparation()` 局部；计划取消只通知页面 ReconnectCoordinator。主审让 prepareAttempt 保持待决，连续两次 reconnect 后 dispose runtime：两个 signal 均为 false，两个 20000 毫秒 timer 仍存在，旧 context.setOptions 仍成功。

已失效的凭据刷新等副作用不能及时取消。应由连接条目拥有当前扩展准备事务，在计划取代、关闭、回收和 dispose 时统一 abort、清 timer，并让旧 setter 拒绝。最终 commit 的 plan id 守卫有效，未发现旧 URL 覆盖新 URL；不要扩大结论。

### F12：重连稳定窗口把断开时间也计为稳定 open

位置：`packages/core/src/connection/reconnect.ts:48`。契约：`packages/core/src/shared/types.ts:50`。

retries 为 1、stableThreshold 为 30000；首次 t=0 open，t=5000 断开；唯一重试一直没有 open，t=40000 失败。openedAt 未在早期断开时结束，第二次 decide 用距旧 open 的墙钟时间判断稳定，错误重置重试预算与退避。主审复现两次 decide 均为 allowed true、attempt 1。

应仅根据一次连续 open 生命周期判断稳定，断开后不得让后续失败尝试继续使用旧 openedAt。

### F13：shared replay 因超大新帧丢失可保留的旧帧

位置：`packages/core/src/worker/runtime.ts:224`；对照 `packages/core/src/page/client.ts:845`。

restore 配置 replay true、maxBytes 10、maxMessages 10，暂停后依次收到 2 字节的 ok 和 11 字节消息。Worker 先淘汰旧帧，再发现新帧本身放不下；direct 先拒绝超大帧。主审复现 shared 回放为空，direct 仍回放 ok。两帧均低于文档声明的 4 MiB 单帧硬上限，不属于已知通道差异。

应先判断单帧是否可容纳，再计算是否需要淘汰旧缓存；保留两条 transport 一致的 overflow 计数与事件语义。

### F14：direct 空闲连接条目的寿命改变新 client 的 URL 与冲突行为

位置：`packages/core/src/transport/direct.ts:119`、`:269`；对照 `packages/core/src/worker/runtime.ts:501`。

direct 按构造/dispose 引用计数保留池条目；shared 在最后一个逻辑 client 离开并完成 idle 回收后删除条目。主审对 A open → close → idle，保留 A 实例，再创建相同 id/shared、不同 URL 的 B：原 socket 已关闭，B 仍复用旧 controller 和旧 URL。相应地，不同共享配置在 direct 中也可能持续冲突。

这不等于“同身份不同 URL 应冲突”：存活条目不接受后来 URL 是 ADR 0003 授权的行为。问题是两条 transport 的空闲条目生命周期不同，而 README 承诺相同 client 语义。应明确并统一条目回收与存活 client 再附着策略；不能直接删除池条目却让旧实例继续持有已 dispose controller。

### F15：扩展 endpointOrigin 在换 host 后仍是初始 origin

位置：`packages/core/src/worker/runtime.ts:655`。

extensionContext 闭包总读初始 config.url。主审让 prepareAttempt 从 `wss://example.test/ws` 换为 `wss://new.example/ws`：第二次 onSocketOpen 仍收到 example.test，diagnostics 已为 new.example，违反该字段“与 diagnostics 同口径”的说明。应在 controller 创建后读取当前 endpoint，只有工厂初始化阶段使用初始 URL。

### F16：direct 暂停和回放时，data 不等于最近已派发消息

位置：`packages/core/src/page/client.ts:591`、`:791`。契约：`packages/core/src/shared/types.ts:547`。

handleMessage 在判断 suspended 前更新 currentData，恢复时直接 dispatchMessage 又不更新它。主审暂停后收到 a、b：尚未派发时 data 已为 b；回放 a 的 handler 读取 data 仍得到 b。shared 回放逐条经过 handleMessage，行为不同。应在真正派发时更新 currentData，暂停缓存不提前改变公开 data。

### F17：jitter 之后的实际延迟超过公开 maxDelay

位置：`packages/core/src/connection/reconnect.ts:17`。契约：`packages/core/src/shared/types.ts:44`。

先对指数基准做 min(maxDelay)，再乘抖动，没有最终上限。主审以 initialDelay/maxDelay 为 1000、jitter 为 0.2、random 为 1，得到约 1200 毫秒。默认 30 秒上限同理可接近 36 秒。若维持“单次重试允许的最大延迟”契约，应在抖动后 clamp；若要保留对称抖动，必须明确修改公开字段含义与规格。

### F18：connectionTimeout 的合法值集合随 transport 改变

位置：`packages/core/src/config/normalize.ts:336`；`packages/core/src/worker/control.ts:140`。

页面 normalize 接受正有限数，Worker parser 要求正整数。主审以 1000.5 创建配置成功，shared open 拒绝 INVALID_CONTROL_MESSAGE。direct 不经过此 parser。应统一接受集合；如要求整数，应在公开创建边界抛 INVALID_OPTIONS，而非到 Worker 才把合法创建结果判为协议错误。

### F19：扩展指南错误承诺 at-least-once

位置：`packages/docs/site/guide/worker-extensions.md:54`。

库允许 credit overflow、replay overflow、lease 和 Worker 回收导致消息一次也不投递，且没有服务端 Ack/retry 协议保证补发。示例在 fan-out 前把 id 写入 seen；即使第一次投递被 credit 丢弃，之后重发也会被过滤。可重复不等于至少一次。

应描述为有界、尽力而为、可能重复也可能丢失；应用按自身事务与服务端协议提供需要的可靠性。这是实现路径与文档逐项对照确认的契约错误，没有新增端到端服务器交付实验。

## P3：公开说明与调用一致性

### F20：ConnectionSnapshot.attempt 并非单调物理尝试计数

位置：`packages/core/src/shared/types.ts:228`；`packages/core/src/connection/controller.ts:478`。

公开字段称为单调计数，实际返回可在显式 reconnect 和稳定窗口后 reset 的 retry.attempt。源码另有真正用于代际隔离的 activeAttempt。应返回符合契约的计数，或明确将公开字段改称可重置的重试计数，避免应用用它判定新旧事件。此项由字段赋值与 reset 调用链核验。

### F21：dispose 后 Promise API 同步 throw

位置：`packages/core/src/page/client.ts:298`、`:367`。

sendMessage/reconnect 不是 async 函数，先调用会同步抛错的 assertUsable，再返回 Promise。主审对已 dispose client 调用两者均观察到同步 CLIENT_DISPOSED；因此 `ws.sendMessage(...).catch(...)` 捕获不到。公开说明要求失败通过 Promise rejection 表达。应统一失败通道或如实修改契约。

### F22：README 中的当前首发版本与包版本不一致

位置：根 `README.md:9`；`packages/socketfuse/README.md:3`；`packages/socketfuse/package.json:4`。

README 仍描述正在准备 0.0.1-beta.1 首发，当前包元数据已是 0.1.0-beta.2，且安装说明仍写“首次发布后”。应更新当前状态，或去除容易过期的首发版本描述。本轮未查询 npm 外部状态，因此不据此断言某个版本已经公开发布。

## 架构与规范判断

### 有源码支撑的边界

- Worker 同步 hello 事务通过 Map 唯一创建连接，并重建 canonical/fingerprint。冲突比较 canonical 原文，不能用短 hash 碰撞直接推导静默混用配置。
- endpoint 不属于共享身份；当前 plan 才能原子提交 URL/delay，旧 plan 的最终提交守卫有效。
- Worker 普通 fan-out 不等待页面 handler；receipt 在页面业务派发前归还 credit，它不是服务端或业务 Ack。
- Worker 扩展准备与页面候选机制只选一个来源；应用协议状态仍由应用拥有。
- 三个公开入口在 import 时没有创建页面 client/socket，facade 创建时有浏览器 realm 检查。零运行时依赖、私有 core 打包、ws 仅在测试 workspace 的边界保持。

### 需要收紧的职责边界

问题集中在两套 transport 的生命周期和数据派发差异、取消状态的所有权、await 后的代际检查，以及内存计费口径。优先完善现有模块的不变量和回归场景，没有证据要求新增一层通用抽象或推翻 SharedWorker-first 结构。

`connection/controller.ts:23` 从 `transport/socket.ts` 导入运行时值，字面上逆于 AGENTS 的依赖层次；socket 是只依赖 shared 的叶子，未发现文件级运行时值循环。应在现有模块职责中明确原生 socket 能力面的归属；这是结构规范偏差，不能包装成已复现的循环依赖故障。

### shared/direct 差异清单

| 行为 | 当前文档与实现判断 |
| --- | --- |
| 跨标签页共享 / 当前 realm 连接池 | 已声明。 |
| execution key 跨页唯一 / direct 每 client 自持 | 已声明，但 shared 的失效授权启动问题见 F01。 |
| shared delivery credit 与 4 MiB 单帧硬上限 | 已声明；实际内存估算另有 F04。 |
| Worker 静态 maxPorts、envelope、key 总额度 | configuration 有描述；transport README 的“唯一例外”措辞不够准确。 |
| open 取消与等待期限 | 未声明差异，且违反公开操作契约，见 F08–F09。 |
| close 后 reopen、空闲条目回收 | 差异影响可用性、URL 与冲突结果，见 F02、F14。 |
| replay 与公开 data | 未声明差异，见 F13、F16。 |
| Worker 扩展在 direct 中不可用 | 扩展需 custom Worker 有说明，但默认 fallback 会失去过滤/共享准备能力，应明确提示依赖该能力的部署选择相应策略。 |
| custom adapter 的执行 realm | 公开类型称“只能在 custom Worker 内执行”，但 direct 使用页面保留的 adapter；应明确 fallback 的真实行为及错误边界。 |
| diagnostics 新鲜度 | shared 是后台请求更新的缓存，direct 是即时 controller 快照；playground README 有说明，公共“瞬时指标”措辞应更精确。 |

### 已排除与未升级的候选

以下不属于缺陷：同共享身份不同初始 URL 可以加入；普通消息仍广播给非 holder；receipt 先于业务 handler；Worker 内有期限的异步 prepareAttempt；已经启动的 Promise 无法被强制终止；扩展的过期 setter 不等于旧 URL 最终提交成功。

以下仅保留为后续定向审查候选，未计入最终 findings：挂起 adapter 导致 outgoingTail/OrderedProtocol 在后段额度之前积累；shouldReconnect 抛错的状态机隔离；URL fragment 与原生构造校验集合。当前证据不足以对其完整影响和修复范围下结论。
